## 1. What changed

### Decision 1: v1 is 1v1 only

- **`src/types.ts`**: new constant `PLAYERS_PER_SESSION = 2`.
  `MAX_PLAYERS_PER_ROOM` now equals it (it was 4). `Room.playerIds` is still
  an array, so allowing more players later means changing one number and
  the rules, not every type. `spectatorIds` stays in the type, marked unused.
- **`src/session.ts`**: new rule `hasRightPlayerCount(playerIds)`. It's in
  the rules file so there's one place to change later. `startProblem()`
  uses it, so a session can't start without exactly 2 players.
- **`src/pages/lobby.ts`**: shows "Players (2/2)" and says "You need exactly
  2 players". Removed the spectator count and the 3–4 player [OPEN] note.
- **`src/pages/results.ts`**: removed the "3–4 player records" [OPEN] note.
  Every session is now recorded in head-to-head and the leaderboard.

### Decisions 2 and 3: one Session options screen, host-only

- **Removed** `pages/setup.html`, `pages/handicaps.html` and their scripts.
- **New** `pages/options.html` + **`src/pages/options.ts`**. One screen
  with: players, format, number of games, game selection, a per-game
  "best-of-3" checkbox, randomized order, handicaps (player stats, suggested,
  custom), and the "Require two confirmations" checkbox. It ends with
  **Start the session**. (`git` tracks `setup.html → options.html` as a
  rename. `options.ts` changed too much to count as one, so the old script's
  history is under `src/pages/setup.ts`.)
- **Host-only:** the page checks `user.id === room.hostId`. For the host,
  every control works. For the other player, the same controls are drawn
  but `disabled`, and host-only buttons (Randomize, Start, Add/Remove
  handicap) aren't shown. If the host hasn't opened the screen yet, the
  other player sees "Waiting for the host".
- **Every change saves immediately**, then the page redraws itself from the
  saved state (see "New concepts"). In the real app, saving straight away is
  what would let the other player see the host's choices live.
- **`src/types.ts`**: `Session` gained `selectedGameIds` (what the host
  ticked) and `bestOf3GameIds`. The fields are grouped with comments:
  options, play order, play.
- **`src/session.ts`**: the setup rules moved here from the page:
  `createSession` (defaults, or copy a previous session's options),
  `randomizeOrder`, `clearOrder`, `isOrderRandomized`, `startProblem` (why it
  can't start yet, shown on screen) and `startSession`.
- **Best-of-3 moved** from a per-round checkbox on the Round page to the
  options screen. The Round page now just says "Play this game as a
  best-of-3". Daily games (Wordle, Connections) can't be ticked (assumption
  Q3 below).
- **Play again** (`src/pages/results.ts`) is host-only and opens Session
  options with the previous session's options carried over. The order is
  re-randomized (assumption Q4).
- **Links and routes:** `src/routes.ts` has `options` instead of `setup` and
  `handicaps`. Every link was updated (lobby, games, results, round, between
  pages, and the static links in `pages/*.html`). `npm run check-links`
  confirms nothing points at the old pages.
- **`src/state.ts`**: storage key bumped from `botb-prototype-v1` to `-v2`,
  because the saved `Session` shape changed. Old saved data is ignored, not
  crashed on (tested).

### Decision 4: result reporting and "Require two confirmations"

- **Off (the default):** unchanged. One player's report is final.
- **On:** a report goes into a new field, `Round.pendingReport`, instead of
  `Round.outcome`. Only the *other* player sees **Confirm** / **Reject**.
  The reporter sees "Waiting for sam to confirm or reject it". Confirm makes
  it final. Reject deletes the pending report so either player can report
  again. This is labelled `[Placeholder: …]` on the page; see Q1.
- **Ties count as results too.** With the option on, a reported tie is
  pending as well, and the substitute game is only chosen once confirmed (Q2).
- **`src/types.ts`**: new `PendingReport` type; `Session.requireTwoConfirmations`;
  tie outcomes now record `reportedBy` and `confirmedBy` too.
- **`src/session.ts`**: `reportWin`, `reportTie` (replaces `scratchTie`),
  `canRespondToReport`, `confirmReport`, `rejectReport`. The page never
  decides who may confirm; it asks the rules.
- **`src/pages/round.ts`**: shows one of three things: report form, "waiting",
  or Confirm/Reject. The old [OPEN] note is gone.
- **`src/score-view.ts`**: round history says "…, reported by sam, confirmed by alex".

### Decision 5: "View as" switch (prototype only)

- **New `src/view-as.js`** (plain JavaScript). It sits in the footer of every
  page, under the site map and Reset button: **PROTOTYPE ONLY: View as:

### Decision 8: a tied session stays a tie

- **`src/session.ts`**: the comment on `finishIfDecided` now records the decision.

### Decision 9: confirmed assumptions

None of these had code [OPEN] notes. They were assumptions A1–A5 and A13
in `FOUNDATION_NOTES.md`, now marked ✅ there. The behavior is unchanged,

The **Log out** button (and, at first, View as) saved the copy of state loaded
when the page opened. On a page that had saved changes since (Session

6. **View as: host (alex)** → **Start the session →**.

**B. A full best-of-3 with a tied round (one report is enough)**
1. Round 1: press **Tie** → Between rounds shows the round scratched and the
   substitute as the next game. **Start next round**.
2. Report alex, then sam, then alex. After the second alex win: **alex wins!**
   (4 rounds in history, one scratched).
3. **View as: other player**: no Play again button, just "The host can start
   a rematch". Switch back to host.
4. Friends / Leaderboard: alex vs sam is now 8–5. The leaderboard is ordered
   by total wins.

**C. Two confirmations and a tied session**
1. Results → **Play again with the same room**. Your options are still set.
2. Tick **Require two confirmations**. Set Number of games to **2** (note the
   "can end in a tie" warning). Start.
3. As alex, report **alex** won. The round page now says *Pending… Waiting for

4. **View as: other player** → **Reject**. The report form is back. As sam,

5. **View as: host** → **Confirm**. History says "reported by sam,
   confirmed by alex".
6. Next round: as alex, press **Tie**. It's pending. As sam, **Confirm**:

**D. Joining instead of hosting** (optional)

## 3. New concepts

**"Change the data, then redraw from the data."** The old setup page kept
some things only in page variables. The new options page has one function,
`render()`, that builds the whole page from the saved session. Every
control's handler goes through `update()`, which (1) changes the session,
(2) saves it, and (3) calls `render()` again. The screen can't drift out of
sync with what's saved, and nothing can change without being saved. This is
the core idea of UI frameworks like React, done by hand.
`root.replaceChildren()` (empty the element) followed by `mount(...)` is the
redraw.

**`disabled` for a read-only view.** Any `<input>`, `<select>` or `<button>`
with the `disabled` attribute can't be clicked or changed, and the browser
greys it out. The page draws the same controls for both players and just
sets `disabled: !isHost`. Note this is only UI. With a real backend, the
*server* must also refuse option changes from non-hosts, because anyone can
remove `disabled` in devtools.

**Pending state.** A pending report is stored separately
(`Round.pendingReport`) from a final one (`Round.outcome`). Scores, "is this
round over?" and "is the session decided?" only ever look at `outcome`, so
they didn't need to change at all to support confirmations. Keeping
"proposed" and "final" in different fields is a common trick for approval
flows.

**Stale state.** A page loads state once at the top (`const state =
loadState()`). If you keep that object around and save it *later*, after
something else has saved newer data, you overwrite the newer data with the
old copy. That was the Log out / View as bug. The fix is to load fresh just
before changing and saving. The same problem appears with a real backend as
"lost updates", where two clients save over each other.

**`'change'` vs `'input'` events.** The Number of games box listens for
`change`, which fires when you commit a value (Enter, Tab away, arrow
buttons), not for every keystroke (`input`). Otherwise typing "10" would
redraw the page after the "1".

**Plain JS inside a TypeScript project (`allowJs` and JSDoc).** Browsers run
JavaScript, and Vite already handles `.js` files, so `src/view-as.js` just
works at runtime. TypeScript, however, refuses to import a `.js` file unless
`allowJs` is on. With `allowJs` (and `checkJs` left off), TypeScript reads
the `.js` file to learn what it exports but doesn't report errors inside it.
The `/** @param {…} */` comments are **JSDoc**: optional type hints in
comments. TypeScript reads them, so the call in `page-chrome.ts` is still
checked. You can write more `.js` files the same way.

**Arrow functions vs `function` declarations, and TypeScript narrowing.** In
`round.ts`, `afterChange` is `const afterChange = () => {…}` rather than
`function afterChange() {…}`. A `function` declaration is "hoisted": it can
be called from above the line it's written on. So TypeScript can't assume an
earlier `if (!round) …` check has already run, and complains that `round`
might be undefined. An arrow function stored in a `const` only exists after
that line, so TypeScript keeps the "it's defined" knowledge. There's a
comment where it happens.

**`structuredClone`** (used when copying handicaps for Play again): makes a
deep copy of an object. Editing the copy can't change the original, which a
plain `{ ...obj }` doesn't guarantee for nested arrays/objects.

## 4. Questions for me

1. **What should "Reject" do?** *(placeholder from decision 4)* Right now it
   silently deletes the pending report, and either player can report again.
   Nothing records that a rejection happened. Options: keep that; require a
   reason; let the rejecter immediately submit the result they think is
   right (which then needs the original reporter's confirmation); or show a
   "disputed" state for players to sort out verbally.
2. **Should reporting a tie need confirmation when the option is on?** I
   assumed yes, since a tie is a result and scratches the game. Say if ties
   should stay one-click.
3. **Best-of-3 is per game, not one checkbox for the whole session.** I read
   "just a checkbox" as a checkbox per game, so chess can be best-of-3 while
   Wordle isn't. Daily games can't be ticked, because they can't be replayed. Is
   per-game right, or do you want one global checkbox?
4. **Play again carries the previous options over** (format, games, best-of-3s,
   handicaps, confirmation setting) but re-randomizes the order. OK, or should
   a rematch start from defaults?
5. **Leaderboard tie-break:** equal total wins → fewer sessions played ranks
   higher. Alternatives: alphabetical, or share the rank.
6. **Can the host start before the other player is "ready"?** Right now the
   host just presses Start. There's no ready-check from the other player.
7. **Should the host be able to change options mid-session** (e.g. turn on
   two confirmations after a dispute)? Currently options lock at Start.
8. **Does a tied session break a win streak?** Currently it doesn't change
   either player's streak (behavior from before; I didn't change it).
9. **Who can click "Start next round" and report?** Both players can, as
   before. With a real backend you may want both to see the same round
   at the same time; that's part of the real-time question.
